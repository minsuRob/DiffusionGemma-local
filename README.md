# DiffusionGemma Local

로컬(Apple Silicon)에서 [DiffusionGemma](https://blog.google/innovation-and-ai/technology/developers-tools/diffusion-gemma-faster-text-generation/)를
MLX로 구동하고, 웹 채팅 UI와 SSE 스트리밍 서버로 여러 기기에서 함께 쓰는 구성.

- 모델: [mlx-community/diffusiongemma-26B-A4B-it-4bit](https://huggingface.co/mlx-community/diffusiongemma-26B-A4B-it-4bit)
  (26B MoE / 활성 3.8B, 4-bit 양자화 ≈ 16.5GB)
- 런타임: [mlx-vlm](https://github.com/Blaizzy/mlx-vlm) — 디퓨전 디코딩(`diffusion_gemma`) 네이티브 지원
- 검증 환경: MacBook Pro M5 Max / 36GB

## 설치

```bash
python3 -m venv .venv
.venv/bin/pip install -U mlx-vlm huggingface_hub jinja2
.venv/bin/hf download mlx-community/diffusiongemma-26B-A4B-it-4bit
```

## 웹 서버 (권장)

```bash
.venv/bin/python server.py
```

실행하면 액세스 토큰이 포함된 LAN URL을 출력한다. 같은 네트워크의 폰·태블릿·다른 맥에서
그 주소를 열면 바로 쓸 수 있다.

```
Open on any device on this network:
  http://192.168.0.10:8842/?token=Xc9f...
```

주요 옵션: `--port` (기본 8842), `--host`, `--max-context` (기본 96,000),
`--max-tokens` (기본 1024), `--token` (고정 토큰; 생략 시 매 실행마다 랜덤 발급).
`DIFFUSIONGEMMA_TOKEN` 환경변수로도 지정할 수 있다.

diffusion 관련 옵션 둘:

- `--unmasking-interval` (기본 2) — 몇 스텝마다 언마스킹 미리보기를 보낼지. 미리보기
  갱신 주기가 대략 이렇게 바뀐다 (877토큰 답변, 설정당 2회 측정):

  | 값 | 프레임 수 | 갱신 간격 |
  |---|---|---|
  | 1 | 45~53 | 190ms |
  | 2 | 29~30 | 378ms |
  | 4 | 19~21 | 595ms |
  | 8 | 11~12 | 950ms |
  | 0 | 0 | 미리보기 없음 |

  매 프레임 `mx.eval`로 GPU를 동기화하지만 생성 속도에 미치는 영향은 측정되지
  않았다 — 전 구간 80~111 tok/s로 실행별 편차 안에 묻힌다. 26B forward 패스에
  비해 캔버스 하나 디토크나이즈하는 비용이 무시할 수준이라 그렇다.
- `--canvas-length` (기본: 모델 config의 256) — 한 캔버스에서 denoise할 토큰 수.
  줄이면 확정 텍스트가 더 자주 갱신되지만 denoising 패스가 늘어 tok/s가 떨어진다.

### 기능

- 첨부 화면과 같은 대화 목록 사이드바 (검색, 새 채팅, 삭제)
- SSE 스트리밍 (마스크가 풀려가는 캔버스 미리보기 + 확정 텍스트), 대기열 순번 실시간 표시, 생성 중지
- 추론 채널(`생각하는 과정 표시`) 접기/펼치기
- 마크다운 + 코드블록 렌더링, LaTeX 수식 평문 변환
- 대화 기록은 서버 `conversations.db`(SQLite)에 저장되어 기기 간 공유

## OOM 방지 설계

모델은 상주 17GB, 긴 컨텍스트에서 28GB까지 쓴다. 36GB 머신에서 **두 번째 생성이 동시에
돌면 느려지는 게 아니라 그냥 죽는다.** 그래서 동시성은 병렬 실행이 아니라 대기열로 처리한다.

| 장치 | 동작 |
|---|---|
| 단일 워커 직렬화 | 생성은 언제나 한 번에 하나. 나머지는 큐에서 대기하며 순번을 SSE로 받는다 |
| 대기열 상한 8 | 초과 요청은 503으로 즉시 거부 (무한 적체 방지) |
| 중복 실행 차단 | PID 락파일 + `mlx_vlm.server` 프로세스 스캔. 두 인스턴스는 ~34GB라 하드 스톱 |
| 포트 사전 점검 | 모델 로드(3초) 전에 바인드 가능 여부를 먼저 확인 |
| 컨텍스트 예산 | 기본 96K, 하드 상한 120K. 초과 시 오래된 턴부터 자동 제외 |
| 청크 프리필 | `prefill_step_size=2048`. 없으면 ~16K에서 Metal 버퍼 한계로 OOM |
| 캐시 정리 | 작업이 끝날 때마다 `mx.clear_cache()` |

> **주의**: `mlx_vlm.server`(OpenAI 호환 API)를 쓰려면 `server.py`를 먼저 내려야 한다.
> 둘을 동시에 띄우면 모델이 두 번 로드되어 즉시 OOM이다. `server.py`는 이를 감지해
> 시작을 거부하지만, 반대 순서로 띄우면 막아주지 못한다.

OpenAI 호환 API가 필요할 때 (openclaw 등 외부 클라이언트 연동):

```bash
.venv/bin/python -m mlx_vlm.server --model mlx-community/diffusiongemma-26B-A4B-it-4bit --port 8080
```

## 이미지 다루기

`＋` 버튼, 드래그, 붙여넣기로 이미지를 올린다. 두 가지 모드가 있고 기본은 읽기다.

| 모드 | 쓰임 | 검증 |
|---|---|---|
| **이미지 읽기** (기본) | 스크린샷, 사진, 표가 아닌 아무 이미지 | 없음 — 1회 판독 |
| **표 추출** | 영수증·거래내역서처럼 스키마에 맞는 표 | 3패스 합의 + 형식 검증 |

읽기 모드는 입력창에 질문을 함께 쓰면 그 질문에 답한다. 비워두면 **무엇인가 → 핵심 내용 →
특이사항** 순서로 분석한다. 전사가 아니라 분석이므로 글자를 전부 옮기지는 않는다.

### 추론을 먼저 한다

두 모드 모두 읽기 전에 모델이 이미지를 판단한다. mlx-vlm이 `enable_thinking`을 강제로
False로 주입하고 있어서(`prompt_utils.py:806`) 지금까지 모델의 추론 채널이 한 번도 켜진
적이 없었다. 이제 필요한 곳에서 켠다.

- **읽기 모드**: 추론을 켜고, 그 과정을 `생각하는 과정 표시`로 접어서 보여준다
- **표 추출**: 타일을 읽기 전에 전체 이미지를 한 번 보고 문서 종류·열 구성·스키마 대응을
  판단한다. 결과는 표 위에 파란 블록으로 뜨고 판단 근거도 펼쳐볼 수 있다

**타일 판독에서는 추론을 켜지 않는다.** 켜면 모델이 thought 안에서 행을 다 읽어놓고 예산이
끊겨 답변을 못 내놓는다(실제로 겪었다). 추론은 사전 패스에서 한 번 하고, 타일은 그 결과를
전제로 기계적으로 옮긴다.

표 추출은 스키마가 정의한 열을 찾으므로, **그런 표가 없는 이미지에서는 0행이 나온다.**
이때는 아무 행도 못 찾았다고 표시하고 모델이 실제로 뭐라고 답했는지 보여준다. 0행을
"전부 검증 통과"로 표시하면 이 도구가 막으려는 바로 그 조용한 성공이 되기 때문이다.

## 표 데이터 추출

영수증·거래내역서처럼 표가 있는 이미지를 구조화된 데이터로 뽑는다. CLI도 있다.

```bash
.venv/bin/python extract.py page.png --schema schemas/ledger.json
```

### 왜 나눠서 읽는가

모델은 이미지를 무조건 224×224로 줄이므로 **원본 해상도는 정확도와 무관하고**
(640px과 3840px이 동일하게 100%), 한 장에 든 글자 수만 문제가 된다.

| 한 장에 든 행 수 | 필드 정확도 |
|---|---|
| 10행 | 100% |
| 20행 | 85% |
| 30행 | 91% |
| 45행 | 66% |

그래서 가로 투영 프로파일로 글자 줄을 찾아 **줄 사이에서만** 잘라 타일로 나눈다.
45행 합성 문서 기준 결과:

| | 필드 정확도 | 소요 |
|---|---|---|
| 통짜 1패스 (기준선) | 43.9% | 5.4s |
| 타일 5개 × 3패스 | **99.4%** | 20.3s |

**타일은 반드시 한 호출에 한 장씩 보낸다.** 이미지는 토큰 수보다 메모리를 훨씬 많이
써서, 8장 19.3GB / 16장 22.0GB / 32장 27.5GB(출력 붕괴)였다. 한 장씩이면 17.7GB에 머문다.

### 조용한 치환을 드러내는 법

남는 오류는 `INV-65642 → INV-56642`, `LFAH → LLAH` 같은 치환이라 형식이 멀쩡하고
에러도 없다. 크롭 위치를 바꾸면 오류가 달라지므로, 크롭을 조금씩 옮긴 3패스를 읽고
필드 단위로 다수결한다. **`temperature=0`이라 같은 크롭은 같은 답을 내므로, 패스를
나누는 의미는 오직 크롭을 다르게 하는 데 있다.**

| 상태 | 뜻 |
|---|---|
| `ok` | 3패스 전원 일치 + 형식 검증 통과 |
| `majority` | 2/3 일치 — 다수값 채택, 확인 권장 |
| `resolved` | 불일치했으나 해당 행만 확대 재판독해 확정 |
| `conflict` / `unresolved` | 확정 실패 — 값을 비우고 사람에게 넘김 |
| `invalid` | 전원 일치했더라도 스키마 형식 위반 |

세 패스가 **같은** 실수를 할 수 있으므로 스키마 검증은 다수결과 독립적으로 돌린다.
한 패스가 행을 통째로 놓친 것도 침묵이라, 관측 횟수(`seen`)가 부족한 행은 따로 표시한다.
키 자체를 오독해 갈라진 행(`INV-50580` vs `INV-60580`)은 편집거리로 원래 행에 합쳐
행 수를 맞추고 코드 불일치를 드러낸다.

측정: 45행 문서에서 **정확도 99.4%, 경고 없이 틀린 필드 0개**, 검토 필요 9/45행.

### 사전 파악이 하는 일

열 순서를 섞고 스키마에 없는 열을 두 개 섞은 문서(`tests/fixtures/ledger_shuffled.png`)로
사전 패스의 유무를 비교했다.

| | 필드 정확도 | 조용한 오류 | 호출 |
|---|---|---|---|
| 사전 패스 없음 | 66.7% | **14** | 10 |
| 사전 패스 있음 | **100%** | **0** | 10 |

조용한 오류 14건이 핵심이다. 세 패스가 **모두 같은 열 매핑 실수**를 했기 때문에 다수결이
만장일치로 틀린 값을 통과시켰다. 다수결로는 잡을 수 없는 종류의 오류이고, 사전 파악만이
막을 수 있다. 호출 수와 시간은 사실상 같다(사전 패스 1회가 늘지만 타일이 헤매지 않는다).

표가 아닌 이미지는 사전 패스에서 **모델 호출 1회로 중단**한다(이전에는 3회를 헛돌았다).

스키마는 `schemas/*.json`에 둔다.

```json
{
  "name": "ledger",
  "row_key": "code",
  "fields": [
    { "name": "code",   "type": "string",  "pattern": "^INV-\\d{5}$" },
    { "name": "amount", "type": "number",  "min": 0 }
  ]
}
```

## 측정 결과

### 생성 품질·속도 (`bench.py`, 8종 프롬프트)

사실 질문·한국어·추론·코드·산수·요약·창작·JSON 8개 전부 정상 출력.
생성 속도 **51~208 tok/s**, 평균 약 120 tok/s. 자기회귀 모델과 반대로 **출력이 길수록 빨라진다**
(256토큰 블록을 병렬 생성하는 디퓨전 디코딩 특성). 424토큰 추론 답변이 3.4초.

### 입력 길이 (`limits.py`, 출력 1024토큰 기준)

| 입력 토큰 | 피크 메모리 | 총 소요 | 생성 속도 |
|---|---|---|---|
| 77K | 24.6GB | 66초 | 34 tok/s |
| 96K | 26.5GB | 94초 | 27 tok/s |
| 116K | 27.9GB | 131초 | 25 tok/s |

회귀식 `피크GB ≈ 18.0 + 0.085 × (입력K)`.
모델 스펙 최대는 262K지만, 36GB 기준 실질 한계는 **~120K**이며 기본값을 96K로 두는 이유는:

1. `iogpu.wired_limit_mb` 기본값이 약 27GB(36GB의 75%)라 116K는 이미 그 선을 넘는다
2. 120K면 macOS와 다른 앱에 8GB 남짓만 남는다
3. 메모리보다 지연시간이 먼저 문제 — 116K는 한 턴에 2분, 속도는 8배 느려진다

여유 메모리를 더 쓰고 싶다면 wired limit을 직접 올릴 수 있다(재부팅 시 초기화):

```bash
sudo sysctl iogpu.wired_limit_mb=30720
```

### 동시 요청 (실측)

4개 기기 동시 요청 → 순번 `3 → 2 → 1 → 시작`으로 직렬 처리, **피크 17.63GB 유지**.
9개 큐 적체 상태에서도 피크 17.92GB, 스왑 증가 0.

## 디퓨전 전용 생성 옵션

`stream_generate(...)`에 넘길 수 있는 주요 파라미터:

- `max_denoising_steps` — 디노이징 반복 상한 (속도↔품질)
- `block_length` / `diffusion_max_canvas_length` — 병렬 생성 캔버스 길이
- `diffusion_sampler` — 기본 `confidence-threshold`
